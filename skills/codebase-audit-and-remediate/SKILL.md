# 代码库体检与修复工作流

## 核心原则（比工具更重要）

> **静态检测只能给候选，死亡判定必须复核调用链。**

踩过的两个真实误报（都会导致误删活代码）：

1. **"孤儿模块"用固定运行时文件清单判定 → 误报**
   二级接线源（如 `brep_workspace`、`voice_io`、`fission_orchestrator`）不在清单里，
   它们引用的模块就全被误判。实测误报 12 个中 9 个是活的（`brep_topology` 实体引用 ×62）。
   **正解：从入口做 import 传递闭包（可达性），而不是比对固定清单。**

2. **"主类从未被实例化 = 死代码" → 误报**
   项目常用两种非构造式创建：
   - 工厂：`get_failure_injection()`
   - 单例：`from .m import singleton`
   `exception_ledger`（日志 183 次活跃）就是这样被误判的。

## 五层体检（顺序不可颠倒）

### 第 1 层 · 语法健全性
用 `compile(src, path, 'exec')` 直接编译源码，**不要**用
`py_compile.compile(cfile=os.devnull)` —— Windows 上 `os.devnull` 是 `nul`，
py_compile 会拒绝写并报 `nul is a non-regular file`。

### 第 2 层 · 可达性接线（正确做法）
```
入口 = [ui.py / main.py, 核心引擎, 主循环]
↓ 做 import 传递闭包（BFS/DFS）
不可达 = 疑似死模块
```
**必须处理相对导入**：`from .emotion import X` 会被 `split('.')` 成 `['', 'emotion']`，
首元素空 → 朴素实现直接返回 None → 导致 `emotion`/`fitness`/`exception_ledger` 全被误判不可达。
正确解析：1 个点 = 与导入方同目录；2 个点 = 上一级。

### 第 3 层 · 死刑复核（对每个候选）
两个独立指标，缺一不可：
- **模块名被提及次数**（可能只是字符串/注释）
- **类/函数实体被引用次数**（真使用）
只有"实体零引用"才算死。抽样复核：对每个候选模块 grep 全库，确认类/函数实体零引用后再动手。

### 第 4 层 · 接线完整性（import 分类）
把所有 import 分成三类，**只有第一类需要修**：

| 类别 | 判定 | 处理 |
|---|---|---|
| **真断链** | 不受保护 + 模块不存在 + 本地/第三方都不是 | 必须修 |
| 可选依赖 | 在 `try:` 或 `except ImportError:` 块内 | 设计如此，不动 |
| 包内绝对/相对引用 | `from pkg.mod import` / 文件内相对引用 | 依赖 CWD/sys.path，非缺陷 |

`except` 块内的 import 也算受保护 —— 那是回退分支
（`try: from pkg.x import A / except ImportError: from x import A`），朴素实现常漏判。

### 第 5 层 · 反模式检测
- **掏空方法**：`def f(): pass` 但**仍在被调用** → 高危。
  ⚠️ 必须排除 `@abstractmethod`（抽象方法无实现体是正确写法）。
- **判据悬空**：`X == "STATE"` 但 `"STATE"` 全项目无人赋值 → 该判据恒假，永远判失败。
  这是"功能看起来实现了但永远不生效"的典型死因。
- **序列化膨胀**：找 checkpoint/快照里最大的字段，看是否无界增长。

## 批量反模式修复（以静默吞错为例）

**安全约束（5 条，缺一不可）**：
1. 只改"目标子句后**紧跟**单行 `pass`"的位置 —— 不碰多语句块
2. 不碰空壳函数（`def f(): pass` 不属于 `except` 块）
3. 已绑定异常名的 `except ... as e:` → 复用 `e`；未绑定 → 追加 `as _e_silent`
4. **保留原始控制流语义** —— 只增加记账，不改变"是否吞掉异常"
5. **落盘前先 `compile()` 验证新内容，失败即整文件回滚**

**复用已有机制**：先搜项目里有没有现成的聚合/上报模块
（如 `exception_ledger`），有就接上，**不要新建**。
好的聚合器特征：按 (模块, 异常类型, 消息摘要) 归类 + 定时上报 + repeat_offenders。

## 清理与回滚

- **优先"移动不删除"**：建 `_quarantine_YYYYMMDD/`，附 README 写清
  每个文件的移出依据 + 回滚命令。用户要的是"工作区干净"，不是"数据消失"。
- **批量改动前先备份**目标文件（`_quarantine/backup_before_xxx/`）
- 只对**确认为可再生**的东西真删：`__pycache__`、0 字节文件、过期 checkpoint
- 分批操作（每批 ≤10 个），逐批核验，失败立即停

## 收尾必做

```
1. 全量编译 0 错误
2. 接线完整性检查: 真断链 0
3. 关键改动点 grep 复核(确认写进去了, 不是"以为写进去了")
4. 运行态验证: 启动后 0 Traceback / 0 ERROR
5. 报"完成"必须带收据: 文件路径 / 日志行 / 测量数字
   —— 没有收据的完成声明是 pending, 不是 done
```

## 常见坑

- **判据悬空（最高发，且最隐蔽）**：消费方读 `state["tension"]` / 调 `obj.method`，但供给方
  **根本没暴露该键**（真名是 `last_tension`）或键存在而**量纲不匹配**（阈值 `0.85` 对实测值 `5~53`）
  → 该判据**恒假**（读不到就当默认 0），"功能看着实现了却永远不生效"。
  查法：把"读键处"与"写键处"拉出来逐一比**名字**和**量纲**；`grep` 供给方的 `def get_state` / `return {`。
  **⚠ 修前必须先测爆炸半径**：把键补上并归一化后，本例比例恒 ≈1.25 → 会**级联触发**
  （真死从历史 13 次变成每 ~100 周期一次）。**正确修法是复用既有的完整判据函数**
  （如 `TrueFission.should_die` 三重确认），而不是自己另写一个阈值判断。
  判据改动前，用**历史发生率反证阈值语义**（系统跑了 3610 代只死 13 次 ⇒ 0.85 绝不是"张力比例"）。
- **契约不一致（判据悬空的近亲）**：供给函数对"某类输入"**提前 return 不注册**
  （如 `record_command_attempt` 对白名单外的中文名**不写** `command_capabilities`），
  而调用方**假设它一定注册**、随后直接下标 `d[cmd]` → `KeyError`，
  **异常消息往往就是那个字符串本身**（看着像"数据坏了"，实为"契约不一致"）。
  查法：`grep` 消费点前的"若不在则调用 register 再下标"模式 → 去核那个 register 是否**对所有输入**都注册。
  修法：消费端改用 `.get()` + `None` 守卫（**别在消费端复刻白名单**，避免两处漂移）；
  `grep -n "d\[" ` 扫同类直接下标，逐个看是否已被 `if x in d` 守护（本例另一个下标点已被守护=安全）。
- **别信终端显示的乱码**：文件可能是干净 UTF-8，只是终端解码不对。
  用脚本 `open(p,'rb').read().decode('utf-8')` 核实后再下"文件损坏"结论。
- **别用 `grep -cE "a+"` 统计字面串**：`+` 会被当正则量词。用 `grep -cF`。
- **"属性 vs 方法"**：调 `obj.is_loaded()` 前先确认它是属性还是方法
  （本项目 `is_loaded`/`latest` 都是属性，按方法调会 TypeError 并被 except 吞掉）。
- **验收 grep 的文案要跟代码同步**：改过日志文案后，旧的验收命令会永远返回 0，
  看起来像"没生效"，实际是 grep 找不到。

## 附层 · 数据账本审计（账本型系统专项）

> 触发：系统有"自我记录"的持久账本（死亡证书/谱系树/审计日志）并对外声称"可审计"。
> 核心：**问题是症状，缺陷是根因。** 审计/审稿发现的问题要落到**系统修复**，不是改报告。

### 三条铁律
1. **来源分层（provenance）**：每条账本记录都要有机器可读的来源字段
   （`production/test/e2e/manual/legacy_unrecorded`）。没有它，审计只能靠字符串猜
   （实测：429 份证书 372 份是测试，全靠 `death_reason` 含 "test" 判）。
2. **测试隔离**：测试**绝不允许**写生产账本。根因常是"单例默认写生产路径"+测试直调业务类
   （实测：`tests/` 调 `TrueFission.die()` → 单例把 314 条"测试自我"写进生产
   `death_certificates.jsonl`）。修法：写入前判 `PYTEST_CURRENT_TEST` 或
   `pytest in sys.modules` → 改写隔离目录（`_test/`），生产路径不变。
3. **不洗白历史**：无凭证的历史记录**如实标 `legacy_unrecorded`**，绝不补造凭证。
   判据**分层判定**（只对 `provenance=production` 的样本生效），历史残留单列 ——
   这不是放宽判据，是分清口径。

### 四个"能否机器判定"的体检问法
- 有多少"已终止但无任何凭证"的记录（悬浮）？
- 每条记录的来源是什么？
- 两个语义相近的字段是否打架（实测 `generation`=89 vs 名字"319世" vs 真实深度 34
  → 加 `lineage_depth` 分离）？
- 账本是否只有内部自洽、无外部锚（→ 加宿主心跳等外部时间戳作锚）？

### 修根因的两条通式
- **全路径**：签凭证的所有路径必须走同一函数（实测漏在"批量导入路径"绕过签发直接设
  `status=dead`，导致 259/276 节点无凭证）。
- **失败留痕**：`except: pass` 是悬浮记录的温床 → 落独立失败账本
  （`*_failures.jsonl` 带 traceback），不阻塞主流程但必须可查。

### 验证三证（缺一不算修完）
1. **编译**：`py_compile` 全部改动文件；
2. **离线端到端**：临时目录跑业务流（`Registry(data_dir=tempfile.mkdtemp())` →
   注册→死亡→查凭证）。**不要**为验证去启动整套系统或触发真实死亡；
3. **运行中**：启动真系统，验三样 ——
   ① 心跳/持久产物时间戳刷新（比 `tasklist` 可靠，沙箱内进程列表可能不可见）；
   ② **pyc 时间戳 > 源码时间戳**（证明加载了新码）；
   ③ 系统**重写账本后新字段仍在**（证明 `to_dict`/`_save` 没丢字段 —— 最易漏的一项）。

### 回填工具的正确姿势
只加字段、不改原值、幂等、落盘前自动备份、先 `--dry-run` 看分布。
**验证规则可信**：让规则分类与已知权威口径对齐（实测规则产出 production=57，
与台账"真死 57"完全吻合 → 规则可信）。
